## Thiruvasagam Pro - Release crash fix

**Problem:** App crashed on launch after Play Store install (release build only, debug worked fine).

**Root cause:** `android/app/build.gradle.kts` had `isMinifyEnabled = true` and `isShrinkResources = true` but NO proguard rules file. R8/ProGuard stripped `androidx.work.impl.WorkDatabase` classes (pulled in by `flutter_local_notifications`), causing:
```
FATAL EXCEPTION: java.lang.RuntimeException: Failed to create an instance of androidx.work.impl.WorkDatabase
```

**Fix:** Created `android/app/proguard-rules.pro` with keep rules for:
- `androidx.work.**` / `androidx.work.impl.**` (WorkManager)
- `androidx.room.**` (Room DB, used by WorkManager)
- `androidx.startup.**` (InitializationProvider)
- `org.bouncycastle.**` / `com.pointycastle.**` (encrypt package, reflection-based)
- `com.google.android.gms.ads.**` (AdMob)
- `com.dexterous.**` (flutter_local_notifications)
- Flutter plugin generated classes, enum values, native methods

Wired into `build.gradle.kts` release block via `proguardFiles(...)`.

**Verified:** Built release APK with dart-define keys, installed on phone (2311DRK48I, Android 16), app launched without crash. AdMob initialized, AppOpenAd loaded, banner/interstitial ad requests flowing.

**Important for Play Store:** Always build with both:
1. `--dart-define=DECRYPT_KEY=rajakavidragonfistsiva1934569690 --dart-define=DECRYPT_IV=dragonfistkavi39`
2. ProGuard rules file must be present (now committed)

## In-app "update available" dialog (hybrid: remote manifest + Play Core)

**Request:** themed, responsive "update available" dialog on the home screen.

**Decision (user chose):** hybrid — custom dialog driven by a remote manifest, with
Google Play Core performing the actual update and a Play Store link as fallback.

**New files:**
- `lib/utils/version_utils.dart` — semantic version compare, tolerates `v` prefix / `-beta`
- `lib/models/app_update_config.dart` — `AppUpdateConfig` (remote manifest) + `PendingUpdate`
  (resolved result). NOTE: class had to be named `PendingUpdate`, NOT `AppUpdateInfo` —
  `in_app_update` already exports `AppUpdateInfo`.
- `lib/services/app_update_service.dart` — singleton. Never throws (all failures collapse to
  "no update"), throttles to 1 check / 6 h, snoozes "Later" for 3 days per version.
- `lib/view/widgets/app_update_dialog.dart` — the dialog.

**Modified:** `lib/view/screens/home_screen.dart` (StatelessWidget → StatefulWidget +
WidgetsBindingObserver; checks after first frame and on resume).

**Dependencies added:** `package_info_plus ^10.2.1`, `in_app_update ^5.0.0`.
`in_app_update` API is v5: `checkForUpdate()`, `performImmediateUpdate()`,
`startFlexibleUpdate()`, `completeFlexibleUpdate()`, `installUpdateListener`.

**ProGuard:** added keep rules for `com.google.android.play.core.**`, `de.ffuf.in_app_update.**`,
`dev.fluttercommunity.plus.packageinfo.**`. Without these the release build would crash the
same way the WorkManager one did.

**Manifest contract (user hosts this himself — DO NOT touch `server/`):**
`https://thiruvasagam.dftacademy.in/version.json`. All fields but `latestVersion` optional.
Minimal form: `{"latestVersion":"1.9.0"}`. Also supports `latestBuildNumber`,
`minSupportedVersion`, `forceUpdate`, `title`, `message`, `releaseNotes[]`, `updateUrl`.

**Gotcha found (important, reusable):** `Responsive.scale()` keys off screen *width* while
`Responsive.height()` keys off screen *height*. On a phone in landscape that inflates text to
1.6x while collapsing vertical spacing to 0.5x, which wrecked the dialog. Fix: the dialog now
uses its own `_Metrics.forWidth(constraints.maxWidth)` (factor clamped 0.85–1.15) via
`LayoutBuilder`, independent of the shared helpers. A dialog's type scale should follow the
container, not the screen.

**Dialog design:** emblem = `AppAssets.logo2` as focal point (its built-in flourish replaced
the `bar1.png` ornament, which rendered as a broken brown slab). `1.8.0 → 1.9.0` transition
instead of two badges. Actions pinned to a footer outside the scroll view. Two body layouts:
stacked/centred when tall, emblem-beside-copy when `maxWidth > maxHeight` (landscape phone).

**Debug-only test scaffolding** (no production effect, safe to delete):
`android/app/src/debug/res/xml/network_security_config.xml` + the `<application>` entry in
`android/app/src/debug/AndroidManifest.xml` allow cleartext to 127.0.0.1 so the dialog can be
tested with `adb reverse`. Override the manifest URL at build time with
`--dart-define=UPDATE_CONFIG_URL=http://127.0.0.1:8099/version.json`.

**Verified on device (2311DRK48I, Android 16):**
- Optional dialog renders correctly in portrait (screenshotted)
- Force variant (`forceUpdate: true`) renders with a single button and survives two BACK presses
- "Later" writes `app_update_snoozed_version=1.9.0` and `snoozed_until - last_checked = 259,224,700 ms` = exactly 3 days
- Release build launches clean and logs `AppUpdateService: HTTP 404 from https://thiruvasagam.dftacademy.in/version.json` — i.e. the check reaches production and fails gracefully (file not hosted yet)

**Not yet done:** `version.json` is not hosted, so no user will see the dialog until it is.
In-app update (Play Core path) can only be exercised by a real Play Store install — a
sideloaded APK always falls through to the store link.

**Env gotcha:** this machine has `http_proxy=http://127.0.0.1:53562` set. `curl http://127.0.0.1:PORT`
goes through that proxy and can return 502 while curl still exits 0, producing a false
"server is up". Use `curl --noproxy '*'` and check `lsof -nP -i:PORT` when testing local servers.

## Follow-up: refactor, tests, and verification round 2

**Refactor:** moved the "should we prompt?" decision out of the service's private methods into
pure functions on `AppUpdateConfig` — `isUpdateAvailable(currentVersion, currentBuild)` and
`forcesUpdateFor(currentVersion)`. Private logic inside a service can silently either nag every
user or never prompt anyone, and neither failure shows up as a crash. Now unit tested.

**Tests added (suite now 39, all passing):**
- `test/app_update_config_test.dart` — 12 tests: version ordering, numeric-not-lexicographic
  compare (`1.10.0 > 1.9.0`), build-number tie-breaks, manifest parsing incl. rejecting junk,
  force-update rules.
- `test/app_update_dialog_layout_test.dart` — 6 tests: portrait stacks the emblem above the
  copy, landscape places it beside, the update button stays fully on screen in landscape,
  short screens keep the actions reachable, tablet, and the force variant has no "Later".

**CRITICAL env gotcha — `flutter test` / `flutter run` fail when the proxy env vars are set:**
```
Unable to connect to flutter_tester process: WebSocketException: Invalid WebSocket upgrade request
```
Dart's `HttpClient` reads `http_proxy`/`https_proxy` from the environment (via
`findProxyFromEnvironment`), so the test runner's loopback WebSocket is routed through the proxy
and rejected. Fix:
```bash
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY -u all_proxy -u ALL_PROXY \
  NO_PROXY=127.0.0.1,localhost no_proxy=127.0.0.1,localhost flutter test
```
This is almost certainly the same reason a test suite was once wrongly reported as unrunnable.

**Onboarding testing gotcha:** `adb shell pm clear` then launching does NOT reliably show the
onboarding screen, because Android auto-backup (`allowBackup` defaults to true and is not
overridden in the manifest) restores `shared_prefs` on reinstall. Kesava confirmed onboarding is
working fine — the flag restore is desirable, not a bug. Don't chase it.

**`run-as` only works on debug builds.** The release APK is not debuggable, so its prefs cannot
be inspected. Use a debug build when you need to read `shared_prefs`.

## Real bug found and fixed: request on every app resume

**The bug.** In `AppUpdateService.checkForUpdate` the throttle timestamp was written *after* the
early return for a failed fetch:

```dart
final config = await _fetchConfig();
if (config == null) return null;          // 404 / offline bails out here
await prefs.setInt(_keyLastChecked, now); // ...so this never ran
```

The comment claimed the opposite. Consequence: whenever the manifest is missing (which is the
case right now — it 404s) or the device is offline, `_keyLastChecked` was never written, so the
6-hour throttle never engaged and **every app resume fired a fresh HTTP request**. `HomeScreen`
re-checks on `AppLifecycleState.resumed`, so this is every background/foreground cycle.

**Measured on device before the fix:** 3 requests over 1 launch + 3 resumes.

**Fix.** Record the attempt *before* the network call — a failed check is still a check.
`ignoreThrottle: true` still bypasses it for a manual check.

**Measured after the fix:** 1 request over 1 launch + 5 resumes.

**Made testable:** `AppUpdateService` now takes an injectable `http.Client`
(`AppUpdateService.forTesting(client:)`), so the throttle and failure paths are unit tested
without a network. Added `test/app_update_service_test.dart` (10 tests) covering: prompt on
newer version, the throttle-after-failure regression (asserts the client is called exactly
once), `ignoreThrottle`, malformed JSON, missing `latestVersion`, current build, `forceUpdate`
pass-through, UTF-8 Tamil decoding, and snooze behaviour.

Suite is now **49 tests, all passing**.

**Lesson:** the same class of bug as the ProGuard crash — a code path that only misbehaves in a
state you are not currently in (here: manifest absent). Worth re-reading the ordering of
"record that we tried" against early returns whenever a throttle/backoff is involved.
